Subject: Support-agent pilot: current scope and decisions needed

Hi,

Before discussing a pilot, here is the exact scope of the first version and the
few policy decisions I need from Support before launch.

What the agent can do today

- Verify a customer before sharing account information or acting on a refund.
  It asks for the email on file and the last four card digits. An unknown email
  and incorrect credentials receive the same generic failure response, so the
  agent does not reveal whether an account exists.
- Issue a full refund when the customer is verified and the transaction is
  settled, not already refunded, less than 30 days old, and $75 or less.
- Ask a short clarifying question when a refund request does not identify the
  transaction.
- Create one support ticket and stop automated account handling for legal
  action, suspected fraud, account closure, transfer requests, verified frozen
  cards, and refund requests that require human review.

What it will not do

- It will not refund an over-limit, old, pending, already-refunded, or partial
  transaction. The current mock ledger supports full refunds only.
- It will not unfreeze a card or invent a reason for a freeze.
- It will not process a transfer; transfers are routed to a specialist.
- It will not override policy because a customer is persistent, upset, or
  claims authority. A code-level guard independently checks every refund before
  any money moves.

Decisions needed from Support

I have chosen conservative defaults where the brief is silent. Please confirm
or revise the following before production:

1. Pending transactions: should they always be escalated, or can they be
   refunded before settlement?
2. Frozen cards: should every refund request be escalated while a card is
   frozen? If Support wants the agent to explain a freeze, please add an
   approved customer-safe `freeze_reason` field to the API.
3. Fraud under $500: I currently escalate every suspected fraud report because
   the amount in a customer message is not authoritative. Should smaller claims
   follow a different route?
4. Partial refunds: should they be supported? If so, the payment API needs a
   remaining refundable balance and atomic partial-refund handling.
5. Boundaries: I interpret “up to $75” as inclusive and “under 30 days” as
   exclusive. Please confirm both interpretations and the applicable timezone.
6. Verification abuse: should failed verification attempts be rate-limited or
   escalated? Please specify the threshold and cooldown.
7. Cumulative refunds: should there be a per-customer automated-refund cap over
   a rolling period? If so, please confirm the amount and time window.
8. Escalation operations: please identify the receiving queue, expected
   follow-up process, and any customer language Support has approved.
9. Chat case boundaries: this prototype treats an escalated request as the one
   active case in that chat. I chose this because a model-only handoff could say
   that Support would follow up without creating a ticket, or retry a declined
   refund after customer pushback. The agent therefore creates the ticket in
   code and stops later automated actions in that chat. The trade-off is that a
   separate request needs a new chat. Should customers be able to handle several
   requests in one chat? If yes, I need case IDs and separate state per request
   before launch.

Once these are confirmed, I can encode the decisions in the guard, evaluation
cases, and customer-facing wording.
